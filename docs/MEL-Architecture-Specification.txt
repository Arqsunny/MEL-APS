Enterprise Architecture & Technical Specification

1. Executive Summary & System Objectives

The Master Equipment List (MEL) Management System is an enterprise-grade BIM integration
platform designed to establish a single, bi-directionally synchronized source of truth for all
mechanical, electrical, plumbing, and process equipment across complex capital project lifecycles.
By bridging multi-model Autodesk Construction Cloud (ACC) environments with external project
controls, procurement systems, and field operations, the platform mitigates the data decay, manual
re-entry errors, and sync-lock friction inherent in legacy workflows.

Core Business & Engineering Objectives
     Eliminate Manual Data Entry: Automated bi-directional parameter synchronization

          between native Revit/Forma models and structured relational database repositories.

     Controlled Staging Gate (Option A Review): High-integrity isolation layer preventing

          unverified field or project-management parameter alterations from corrupting central
          design models without explicit BIM Lead authorization.

     Deterministic Parameter Persistence: Multi-level element mapping schema enforcing

          strict GUID, UniqueId, and spatial indexing across multi-model federations.

     Zero-Desktop-Footprint Automation: Headless batch execution of model parameter

          updates using Autodesk Platform Services (APS) Design Automation API for Revit.

     Real-time Spatial & Attribute Analytics: Contextualized web visualizations utilizing the

          APS Viewer API, providing heatmapping, workset collision detection, and field-ready
          mobile barcode/QR interaction.

System Components & Data Boundaries

    1. Authoring Layer: Native BIM authoring inside Autodesk Revit (Cloud Workshared models in

          ACC) and conceptual context models in Autodesk Forma.

    2. APS Cloud Pipeline: Autodesk Platform Services endpoints handle Model Derivative

          translation, Webhooks notification for model changes, and Design Automation for
          executing C# code headlessly against cloud-hosted .rvt files.

    3. Central Backend Core: Built on .NET 8, providing secure RESTful API endpoints,

          background execution worker services via Quartz.NET, Object-Relational Mapping (ORM)
          via Entity Framework Core 8, and real-time client communication via SignalR.

    4. Data Store: Enterprise PostgreSQL 16 instance configured with the PostGIS extension for

          geometric querying, native JSONB for dynamic parameter payloads, and
          System-Versioned Temporal Tables for complete audit compliance.

    5. Interactive Web Client: Modern Web app built with React, TypeScript, and Tailwind CSS,

          embedding the two-way interactive APS Viewer v7.x for model-driven data editing and
          analytics.

Unit Normalization Protocol

To resolve inconsistencies between imperial and metric models across global design teams, the
system enforces a strict internal normalization protocol:

1. Ingest Layer: All values extracted from Revit models are converted from native internal

     units (e.g., Imperial Feet, Pounds) or display units into standard SI Base Units prior to
     database storage.

2. Storage Layer: Values stored in PostgreSQL floating-point numeric columns are exclusively

     stored in standard SI Units (e.g., Kilograms, Kilowatts, Liters per Second).

3. Egress/Display Layer: The .NET API serializes unit types alongside raw values, allowing

     web clients or downstream target models to request dynamic conversions based on
     localized project unit schemas.

private void ApplyParameterValue(Parameter param, string value)
{
   switch (param.StorageType)
   {
      case StorageType.String:

          param.Set(value);
          break;
      case StorageType.Double:
          if (double.TryParse(value, out double dVal)) param.Set(dVal);
          break;
      case StorageType.Integer:
          if (int.TryParse(value, out int iVal)) param.Set(iVal);
          break;
      }
   }

public class WarningSwallower : IFailuresPreprocessor
{
   public FailureProcessingResult PreprocessFailures(FailuresAccessor failuresAccessor)
   {

      IList<FailureMessageAccessor> failList = failuresAccessor.GetFailureMessages();
      foreach (FailureMessageAccessor failure in failList)
      {

          if (failure.GetSeverity() == FailureSeverity.Warning)
          {

             failuresAccessor.DeleteWarning(failure);
          }
      }
      return FailureProcessingResult.Continue;
   }

   var stagingEntry = new StagingParameterUpdate

      EquipmentId = equipment.Id,
      ParameterGuid = dto.ParameterGuid,
      ParameterName = dto.ParameterName,
      OldValue = dto.CurrentValue,
      ProposedValue = dto.ProposedValue,
      Status = ApprovalStatus.Pending,
      RequestedBy = User.Identity?.Name ?? "External System",
      RequestedAt = DateTime.UtcNow
   };
   _dbContext.StagingParameterUpdates.Add(stagingEntry);
   await _dbContext.SaveChangesAsync();
   return Ok(new { StagingId = stagingEntry.Id, Status = "Pending Approval" });
}
[HttpPost("approve/{stagingId}")]
public async Task<IActionResult> ApproveStagedUpdate(Guid stagingId)
{
   var update = await _dbContext.StagingParameterUpdates

      .Include(s => s.Equipment)
      .FirstOrDefaultAsync(s => s.Id == stagingId);
   if (update == null) return NotFound();
   if (update.Status != ApprovalStatus.Pending) return BadRequest("Update is not pending.");
   update.Status = ApprovalStatus.Approved;
   update.ReviewedBy = User.Identity?.Name ?? "BIM Lead";
   update.ReviewedAt = DateTime.UtcNow;
   await _dbContext.SaveChangesAsync();

#### Workset Conflict & Lock Detection

Before executing an automated sync write-back, the .NET backend queries the model state to
verify that target elements are not locked by active user sessions.

* **Checkout Checking:** Reads Revit `WorksharingUtils.GetCheckoutStatus()` via a preliminary
quick-read container in APS.

* **Soft-Locking System:** If a non-BIM user edits a record on the Web dashboard, the database
places a 15-minute soft lock on that `UniqueId` to prevent simultaneous conflicting submissions.

#### Mobile Field Barcode / QR Scanning Integration
* **Generation:** When equipment records are committed, the server generates a
cryptographically signed QR code encoding the specific `UniqueId` and direct web asset URL.

* **Field Action:** Field crews scan the QR tag via a mobile web device. The app opens the web
dashboard, isolates the 3D model view using `viewer.select(dbId)` and `viewer.fitToView([dbId])`,
and brings up parameter inspection and staging entry forms instantly.
